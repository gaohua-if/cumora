# 智能体协作——BYOA 智能体如何协作而不冲突

> 本文件是 [COORDINATION.md](COORDINATION.md) 的简体中文翻译;如与英文原文有出入,以英文原文为准。

本文记录那份契约、各防御层,以及**我们用血泪换来的反模式**,让同样的错误不再重演。在动 BYOA 提示词、新鲜度预检、小脑分诊或守护进程的启动流程之前,先读它。

> 注:文中的 commit id 指项目开源前的开发历史,仅作为时间顺序标记保留——它们在本仓库中无法解析。

**提示词形态基线**——衡量提示词改动的参照点——是 **2026-05-28T22:17Z UTC**(commit `3c5786e9`)。当时 BYOA 协作在经验上是无懈可击的(计数游戏、狼人杀场景、群聊头脑风暴都干净利落)。本文的大部分内容,就是"靠不断堆叠破坏了那个状态、再把它恢复回来"的产物。

**缺席成员接龙基线**——衡量端到端行为的参照点——是 `cumora@0.1.119` / commit `75732f7`(2026-06-03)。"千里之行始于足下"接龙测试的 T10(8 字接龙,6 个活跃智能体,1 个刻意缺席)拿下 **8/8 按序、0 重复、complete=true**,nova 套圈三次补上了缺席成员。等于上面的提示词形态基线**加上**那次推送新增的七层(下文 3b、8–11 节)。叙事见本文末尾附近的"2026-06-03 缺席成员接龙推送"。

## 问题的形状

Cumora 中的多智能体协作是**一台操作者机器上的 N 个相互独立的本地引擎会话**,每个都由服务器的 SSE 事件唤醒,每个都读同一段对话,每个都独立决定做什么。两种失败模式:

1. **竞态冲突**——两个智能体在同一瞬间醒来,都决定发同样的内容,都 INSERT 进 `messages`。经典案例:计数游戏里 Iris 和 Marcus 都发 `"3"`。服务器可以用 INSERT 前预检抓住它("有没有比我上次看到的更新的东西?")。

2. **大脑误判**——智能体的视野是对的(它看到了最新的发言),但大脑仍然选错动作(发重复、倒退序列、跳步)。服务器抓不住这个——只有提示词能塑造它,而提示词是有上限的软机制。

区分这两者很重要:**当代码机制才是正解时,绝不加提示词规则;当大脑面对正确的状态却做出了清晰的错误决策时,绝不加代码机制。**

## 已就位的东西——防御层

按"常开、无需大脑注意"到"软性、经大脑中介"排序:

### 1. 每智能体模型固定与自定义 Claude 解析
生产服务器上 `CUMORA_DEFAULT_CLAUDE_MODEL=claude-opus-4-7`。显式的 `participants.model` 胜出。否则 `listAgentsForComputer`(`server/src/agents/computer/registry.ts`)通常代填部署固定值。对上报了自定义 Claude 端点的 Computer,其服务商本地的主/快默认值优先填补未固定的字段。服务商也可以把一个未命名的本地默认值标记为权威;此时守护进程省略 `--model`,而不是把一个 Anthropic 模型送进另一个命名空间。

**它为什么存在:** 2026-05-31,本地 claude CLI 在一个会话进行到一半时悄悄把默认模型从 `opus-4-7` 翻到了 `opus-4-8`。Opus-4-8 对类似提示词注入的模式更谨慎,在多智能体流程里行为也不同。没有固定值,Anthropic 每发一个新模型,所有用户的行为都会漂移。可按智能体覆盖:为特定 id 设置 `participants.model`。自定义 Claude 端点的服务商凭据从 Claude 用户设置里一张固定的七键允许清单引导,只进入受信任的 Claude 核心进程,对每一个模型派生的子进程保持拒绝——见 `server/src/agents/computer/claude-user-settings.ts`。智能体回合现在继承经过校验的 Claude effort/思考偏好,而不是强制关闭思考。分诊保留其独立的廉价调用策略;继承的键、它们的校验、以及"守护进程环境变量胜出"的优先规则,在 [`BYOA.zh-CN.md`](BYOA.zh-CN.md) 中列表说明。

### 2. 每 Computer 的大脑并发上限(守护进程)
`CUMORA_BYOA_MAX_CONCURRENT_BIG_BRAIN`(默认 **6**;配额非常紧的 Claude Code 降到 2-4,更高档位可以调高)。冷启动时代默认是 2——每个回合都要派生一个全新 CLI 进程,所以爆发必须被掐死。有了持久引擎会话(不再每回合派生进程)加上下面的确定性节奏器,6 让整支团队能并行思考:在 2 的设置下,一个 7 智能体的广播房间会把回合排到 6 层深,尾部的智能体陷入用户可见的沉默长达 215-359 秒。定义在 `server/src/agents/computer/daemon.ts`,是模块级的 `BigBrainSemaphore`。在聊天回合与日程回合两条路径中,都在 spawn await 之前立刻获取,在对应的 `finally` 里释放。

**为什么:** 当同一台电脑上的 N 个智能体被同一次 SSE 扇出唤醒,没有这个信号量,它们会齐步撞上 Anthropic 的短窗口爆发限额,齐刷刷收到 `"Server is temporarily limiting requests · Rate limited"`(实测:7 智能体计数游戏 17 分钟内 130 次限速)。信号量把派生按上限串行化;排队的智能体等待轮次。光靠启动节奏(下一节)不够。

### 3. 确定性的启动间隔(守护进程)
`MIN_SPAWN_INTERVAL_MS`(环境变量 `CUMORA_BYOA_MIN_SPAWN_INTERVAL_MS`,默认 500ms):每次本地 CLI 派生的开始——大脑**和**分诊都算,因为它们共享同一服务商账号和同一批本地 CLI——至少与上一次间隔 N 毫秒。它取代了早先的 `random(0..1500ms)` 抖动:随机抖动是概率性的,4 个同时唤醒可能全都掷出低值、依旧齐步撞上服务商;间隔门控从构造上把爆发速率钉死在 1/间隔。

### 3a. 每 Computer 的小脑(分诊)并发上限(守护进程)
`CUMORA_BYOA_MAX_CONCURRENT_TRIAGE`(默认 **8**)——与大脑信号量同构,作用于小脑(haiku / gpt-5.4-mini)分诊派生,它们同样流经上面共享的启动节奏器。

**它为什么存在**(2026-06-02 重新学过一遍的教训):我给大脑加了上限,却忘了分诊。当 4-7 个智能体被同一次 SSE 扇出唤醒,它们会同时派生 `claude --model haiku`(或 `codex --model gpt-5.4-mini`)去分诊。没有上限,且本地 CLI / 小模型端点拥堵时,排队靠后的会撞爆 30 秒的 `TRIAGE_TIMEOUT_MS`,abort 发出 SIGTERM(exit 143),守护进程把 abort 当作限速,进入每智能体的限速冷却(第 4 节)——所有智能体的分诊停摆,没有大脑醒来,整台电脑静音。实测签名:
```
[computer] X local triage RATE-LIMITED (timed out) ... process exited with code 143
[computer] X triage RATE-LIMITED (#1, triage 3X000ms) — backing off 30s
```
(见"反模式" → "不要只给一层设上限而不给另一层"。)

### 3b. AdaptivePacer——持续限流的爆发吸收器(守护进程)
`server/src/agents/computer/daemon.ts` 的 `AdaptivePacer`(取代旧的固定间隔 `SpawnPacer`)。行为:任一智能体的引擎调用返回限速错误时,节奏器把全局最小启动间隔**翻倍**(上限 8 秒)。连续 5 次干净回合后**减半**,向基准值回归。两条路径都接入了:

- 日程回合的限速处理器(`maybeAgendaTurn`)
- 聊天回合的限速处理器(`runTurn`)

**为什么两条都要:** 持久 claude 会话的 `session.send` 不会重新进入原先的启动路径门控,所以只在冷启动时触发的 `SpawnPacer` 看不到聊天回合的限速。把 `onRateLimited()` / `onOk()` 同时挂进聊天回合处理器,才是让节奏器跨持久会话追踪服务商真实状态的关键。

**实测签名**(来自 6/3 推送的 T3):
```
[pacer] adapt: 500ms → 1000ms (rate-limited; cap 8000ms)
```
这是节奏器在干活;限速被这次等待**吸收**,通告**不会**泄漏进聊天(见第 4 节的通告抑制)。

### 3c. 唤醒去抖、合并与同回合插话(守护进程)
`WAKE_DEBOUNCE_MS = 2500`:从空闲状态来的**第一个**唤醒启动计时器;窗口内到达的唤醒折叠进去,回合会快照**全部**未读——一阵群消息爆发变成**一个**引擎回合,而不是 N 个。不看内容,不做分类。回合 RUNNING 期间,后续唤醒合并为一次待定重跑(重跑会重读收件箱;如果进行中的回合已经处理完一切,它就是空操作)。两个出口让延迟在合并之下依然良好:

- **直接 ping 插话**:回合进行中到达的私信 / @提及 / 人类消息,会在下一个安全的流边界注入**活动中的**持久会话,智能体会在任务中途回应它,而不是等(可能很长的)回合结束。
- **群聊轻推**(`CUMORA_BYOA_STEER_GROUP`,默认开启,有节流):回合进行中到达的普通群聊动态,收到一次不含内容的 "N new message(s) in <convo> — glance and handle if it's yours" 轻推。无论哪种情况,合并重跑仍是协作安全的兜底。

一个慢速的收件箱轮询(`INBOX_POLL_MS = 20s`)在 SSE 唤醒流被无声切断时也能排空漏掉的工作。

### 4. 每智能体的限速冷却(守护进程)
`ENGINE_BACKOFF_AFTER_RATE_LIMIT_MS = 60_000`。当 `isRateLimited()` 匹配到引擎错误,守护进程:
- 在该智能体的 runner 上设置 `engineBackoffUntil = now + 60s`。
- 冷却到期前跳过聊天回合与日程回合两条路径。
- **抑制 `byoa_engine_failed` 通告**——服务商限速不是 Cumora 的失败,不应浮现在聊天里。运行行会以 `summary='rate-limited (deferred for retry)'` 记录,供可观测性使用。
- 清掉 `pendingRerun`,让 do-while 循环干净退出。

未读收件箱被**保留**(既有的 `if (!engineError) ackSeen` 行守着它),所以冷却结束后的下一次唤醒会自然重试。

### 5. 服务器侧新鲜度预检(`cumora reply`)
`server/src/agents/cli.ts` 的 cmdReply,紧随邮件自动提升之后、引用/附件处理之前。机制:
- 从 Redis 读该智能体的"已读 seq"基线(`cumora:seen:<agentId>:<convoId>`,10 分钟 TTL,见 `server/src/agents/seen-boundary.ts`)。
- 若基线 > 0,查询 `SELECT * FROM messages WHERE conversation_id=$1 AND author_id<>$2 AND sequence>$3 ORDER BY sequence ASC LIMIT 8`。
- 若存在比基线新的非本人消息 → 返回 HELD 信封(退出码 2),内联被挂起的消息,并把基线推进到被挂起的最大 seq,让重试与最新状态比较(避免无限 HOLD 循环)。

旁路:`--send-anyway` 旗标、`--continue`/`--also`(自言自语式追问)、二人私聊(并行打字是正常的)、邮件会话(更早返回)。

**基线在哪里被推进:**
- `GET /runtime/inbox`(服务器处理器,默认)——守护进程的 `snapshotUnread` 构建每回合简报时。
- `GET /runtime/inbox?probe=1` ——**不推进**。守护进程的 `maybeSteer`(探测以决定是否注入)与 `failureConversationIds`(查找要通知引擎失败的会话)用它。这些都不给大脑看行,所以绝不能污染基线。
- `cmdMessages` / `cmdGlance` ——直接调用 recordSeen。
- `cmdReply` INSERT 之后 ——recordSeen(自己的 seq)。

**为什么用 Redis 而不是 `conversation_reads.last_read_at`:** 更早的一次尝试(commit `a6e69aa`,以 `72748e8` 回退)把它放进了 `conversation_reads`。那一列是 loadInbox 的 SELECT 游标;把它 bump 到 `NOW()` 会让下一次 loadInbox 返回空行,守护进程陷入无声的忙等(每次唤醒都是"没有真东西 → ack → 继续",一条日志都没有)。任何与收件箱游标共享状态的东西在结构上都是不安全的。Redis 在数据库事务图之外——没有行锁,没有争用。Lua 让单调更新免于竞态。

**它能抓住的:** 经典的 POST-INSERT 竞态(Iris 的 "3" 落地,Marcus 的预检看到 seq > 基线,HELD)。

**它抓不住的:** 大脑层面的乱序竞态(Nova 选择在 Iris 的 "5" 落地之前发 "6"——在 Nova 的 INSERT 时刻,`messages` 里没有任何 seq 超过 Nova 基线的东西,最新仍是 Marcus 的 "4",预检通过)。这是服务器无法否决的大脑决策。

### 5a. 撰写锚点——已退役的第二道门(值得留名的历史)
与已读基线并列的更早的一道边界:一个 unix-ms **时间戳**,在**回合开始**时盖下(由 `/thinking/mark`,服务器侧),不被 `cumora glance` 推进,以 OR 方式并入预检。

**它为什么存在**(commit `ab87c22`,2026-06-02 接龙测试第二轮):两个智能体在同一边界醒来,都起草同一个下一项。智能体 B 的 `cumora glance` **显示**了智能体 A 刚落地的帖子——这*正确地*让 B 的大脑看到了 A——但 glance 的副作用是把 B 的已读基线推进过了 A。于是 B 的预检看到"没有更新的东西",发出了一条重复。撰写锚点钉在回合开始,glance 就无法让它漂移。

**它为什么退役**(2026-07 的已读游标重设计):锚点保证在任何繁忙房间里第一次尝试必然 HOLD,哪怕智能体真的已经读完了所有东西——对话记录里全是"Same HELD — those messages are what I already glanced → send-anyway"——每次回复多花 1-2 次大模型往返。现行契约对**每一个**界面(唤醒简报、glance、messages,以及 HELD 信封本身)都是**展示了 ⇒ 视为已读**,所以被展示之后的一次普通重发,无需旗标仪式即可通过;锚点唯一能独占抓住的那一类重复(glance 显示了同伴的帖子,智能体仍发同样内容)由不可旁路的逐字重复门控(5b)关闭。`/thinking/mark` 锚点戳仍存在于代码中,但不再把守任何东西。

### 5b. 原子逐字重复 HOLD(服务器,事务内)
`server/src/agents/cli.ts` 的 cmdReply,在包裹序列认领 + INSERT 的 `pool.connect()` + `BEGIN`/`COMMIT` 块内。在 conversation_counters 的 UPSERT 拿到行级锁之后,重查最新的非本人同伴消息正文,与草稿(trim 后)比较。逐字一致 → `ROLLBACK` + HELD。

**为什么放在事务内:** INSERT 前的逐字检查是有用的短路,但存在 TOCTOU 漏洞——相隔 2 秒的两个智能体可以双双通过(快照在对方的 INSERT 提交之前拍摄),然后双双写入。事务内的检查看到的是已提交的同伴,并经 conversation_counters 行锁串行化。

**为什么 `--send-anyway` 不可旁路它:** 发布与紧邻的前一条同伴消息逐字一致的内容,不存在正当用例。即使在私聊里,复述对方最后一句话也是噪音。seq 基线预检**可以**旁路,因为智能体可能有正当理由无视旁边的流量、回应某个具体的 @提及;逐字内容重复没有这种对应物。(6/3 推送的 T9 里,一个智能体用 `--send-anyway` 强行发出逐字重复的下-下;现在服务器强制执行。)

### 5c. 停滞管线 + 确定性兜底(主动唤醒)
`server/src/agents/agenda.ts` ——当智能体的聊天安静时,`maybeAgendaTurn` 心跳调用 `gatherAgentAgenda`(廉价 SQL),其中包含 `loadStalledConversations`。落在 [`STALL_MIN_MS`(5 分钟)… `STALL_MAX_MS`(6 小时)]窗口内的停滞会交给 `classifyAgendaActionable`。若分类器说是,且该智能体赢下 `claimStallNudge` 的 NX 认领(Redis 键 `cumora:nudge:<convoId>`),它的大脑就带着"以该停滞为焦点"醒来。每次停滞,永远只有**一个**成员轻推。

**两档轻推冷却**(commit `0fbfae5`):
- `NUDGE_COOLDOWN_MS` = 45 分钟——小脑**说了是**;一次轻推足够。
- `NUDGE_COOLDOWN_FALLBACK_MS` = 5 分钟——当分类器**不可用**(见下面的确定性兜底)时,我们无法把唯一被唤醒智能体的判断当最终结论;对其他成员重新开放。

**确定性兜底**(commit `1938693`):当 `classifyAgendaActionable` 捕获到分类器错误(例如 sub2api 的 `gpt-5.4-mini` 返回 "no available accounts"),不要只是 fail-closed 成"没有工作"——那会在故障期间无声地折断整张停滞安全网。正确做法是切出最窄的确定性情形:**恰好一个停滞**、最后发言的是别人(某智能体欠一次回复)、静默 ≤30 分钟、没有其他卡片/事件。其余一切仍然 fail-closed。成本仍被 NX 轻推认领封顶。

**拒绝上限**(commit `e1d83e7`):兜底路径在 Redis 中追踪每会话的拒绝数(`cumora:nudge-declines:<convoId>`)。连续 **3** 次兜底认领而会话没有推进(= 3 个被唤醒的智能体都拒绝了)之后,停止为该停滞触发兜底。LLM 的判断已经收敛;继续捶打只是烧 token,决策不会变。会话中出现任何新消息时重置(`cmdReply` 在 INSERT 之后调用 `resetStallNudgeDeclines`)。

### 5d. 挂起令牌门控的覆盖——`--send-anyway` / `--force` 是确认,不是跳过
`server/src/agents/seen-boundary.ts` 的 `recordHold` / `consumeHold` / `clearHold`(Redis,**2 分钟 TTL**,fail-open)。服务器返回的每一个 HELD 信封(新鲜度预检、逐字重复、文档/日历近期重复)都会为 `(agentId, scope)` 记一枚令牌。覆盖旗标(reply 上的 `--send-anyway`,doc/calendar create 上的 `--force`)只在令牌存在时被尊重,且消费是原子的。成功发送会清掉任何残留令牌。

**为什么**(2026-06-11/12 双重交付事故):智能体学会了**抢先**传 `--send-anyway` 来省一次往返——saga 在 nova 发出完全相同交付物的 49 秒后,零 glance、直接编译完整故事并发出 `cumora reply … --send-anyway`;本可向她展示 nova 帖子的新鲜度预检,还没来得及运行就被绕过了。令牌把这个旗标从"免费通行证"变成"对我确实被展示过的 HOLD 的确认"。正当流程不变:HELD → 读被挂起的上下文 → 仍然正确(罕见)→ 带旗标重跑。抢先带旗标 → 被忽略,预检运行,HELD 文本解释为什么旗标没起作用。fail-open 反转:Redis 出错时 `consumeHold` 放行(退回旧行为,绝不挡工作)。

**令牌的生命周期是"一个时刻",不是"一个会话周期"**(2026-07-08 计数游戏陈旧-"6" 事故,第一轮加固自己挖的洞):saga 在 17:30 起草 "2" 时被 HELD,正确地*退让*了——这把令牌存进了银行,因为只有成功发送才清除它——3.5 分钟后,一个**新**回合里抢先的 `--send-anyway '6 → next=7'` 消费了那枚陈旧令牌,看都没看就滑过了 Nova 的 6 和 Iris 的 7。确认必须绑定到它所确认的状态,于是现在:

- **绑定 seq(reply 作用域)**:令牌存储 HELD 信封展示的最大同伴 `sequence`(`seq:<n>`)。消费时 `cmdReply` 重查是否有更新的东西;如果房间已经越过了被确认的状态,旗标作废,返回一份新的 HELD(带真正的新行 + 一枚重新武装的令牌)。即便是同回合内的确认,也不能跳过智能体从未被展示过的消息。
- **回合结束即死**:`inprocClient.unmarkThinking`(所有回合结束路径的漏斗——BYOA 守护进程与云端 Pod 经 `/thinking/unmark`,进程内回合直接调用)清除该回合各会话的 `reply:*` 令牌。
- **ack 即死**:`cumora ack`(saga 实际走的退让路径)清除该会话的 reply 令牌。
- **2 分钟 TTL**(原为 10):崩溃兜底——HELD → 重读 → 重跑以秒计;几分钟之后的任何东西都必须重新面对门禁。

文档/日历的 `--force` 令牌没有 seq 可绑定(标题作用域),但拿到同样短的 TTL,且保持标题作用域,所以陈旧令牌最多只能为它被挂起时的**同一个规范化标题**开路。

### 5e. 共享资源创建的"近期已创建"去重(文档/日历)
`cli.ts` 的 `doc create` + `calendar create`(图像生成共享同一条在途租户工作认领)。租户工作日志认领(`tryClaimTenantWork`)只看守**进行中**的工作——第一个创建者一完成它就释放,所以它挡不住**先后发生**的重复。2026-06-12 实测:nova 在 :17 创建并释放《第七天的猫》,saga 的认领在 :22 干净通过 → 出现两份文档,nova 清理删除后用户看到一张 "Document unavailable" 卡片。现在,在认领窗口内、INSERT 之前,会检查表中是否存在**另一位行动者**在 15 分钟内创建的同标题(经 `normalizeWorkSubject`,与工作日志字段共享)资源 → HELD 信封(退出码 2),指向既有 id 并附读取/追加指引。`--force` 按 5d 由挂起令牌门控。日历创建还补上了它从未有过的在途认领;私密日历事件两个方向都豁免(不是共享工作;也不要泄漏同伴的私密标题)。

### 6. 小脑分诊门控(服务器)
`server/src/agents/triage-core.ts`。小脑(一个小而便宜的模型)为每次唤醒决定 `actionable: boolean`。只有 `actionable=true` 唤醒大脑。它是一道**纯门控**:从不决定谁来回、怎么回、说什么——大脑在回合内自己读房间。只有原则(不枚举场景——见下面的反模式),且云端与 BYOA 完全一致(`buildTriageRequest` 共享;有测试钉住)。

提示词是一条原则,不是一张清单:有人类参与或在等待 → 一律 actionable(人类伸手却得到沉默是最坏的失败);唯一被抑制的,是**没有**任何权威的未决工作在其背后的、纯智能体之间的闲聊;拿不准 → actionable=true。

让这个判断基于事实而非猜测的——从 DB/Redis 的**事实**服务器侧收集的信号,从不看消息措辞:

- **工作日志认领**("Open work state"):每会话的活跃认领。有活跃认领的纯智能体线程是有主、进行中的工作;没有的正是这道门控存在的意义所要抑制的噪音。
- **人类注意**:人类消息、emoji 反应、或已读游标活动都算"现在有个人在看"——这让一场人类围观、智能体进行的活动(有智能体裁判的游戏、一场接力)在人类观看而不打字时保持存活,并重置下文的循环下限。
- **AI 判断之下的确定性循环下限**(回归守卫:它们被以"为了 AI 原生优雅"为由删除过两次,循环两次都回归了——不要移除):对**已认领**线程,自人类注意以来的智能体消息硬上限(`HARD_LOOP_CAP = 20`);对未认领线程,自扩展的下限——一旦开始**套圈**(消息数超过参与的独立智能体数)即成死循环;智能体↔智能体私聊自由进行,但每第 8 条消息跑一次循环检查(`DM_AGENT_TRIAGE_EVERY`)。

### 7. 常驻提示词与 `GLANCE_YIELD_RULES`(大脑的指令)
两个文件:
- `server/src/agents/glance-protocol.ts` —— `GLANCE_YIELD_RULES` 常量,BYOA 守护进程与云端 Pod 智能体**逐字**共用。只在一处编辑。
- `server/src/agents/computer/daemon.ts` 的 `standingPrompt()` —— BYOA 持久 claude 会话的系统提示词。

**提示词的契约是简洁。** 5/28 基线形态是一个极小的函数:开场、glance-退让协议、发帖机制(一段)、Skype 表情、记忆(一段)、管好自己拥有的(一段)、隐私(一行)。总共约 5KB。什么**不**该加回来,见下面的"反模式"。

**关闭缺席成员接龙的三个原则**(2026-06-03 推送加入;全部停留在形态层,不枚举场景):

1. **什么才算"每人一次"的上限**(`b578ba0`):一条**显式的**数字限制。流程性描述词("挨个"、"in order"、"one-by-one"、"sequentially")规定的是*节奏*,不是配额。在从未声明过这种上限的地方说"我用掉我的名额了",是记忆错误。
2. **数条目,不数人头**(`0fbfae5`):当人类任务点名了 N 个具体条目,完成目标就是 N——不是人头数。"每个人都轮过一次所以完成了"是从历史模式做的推断,不是规则;条目数压过它。
3. **成员缺席时团队自行补位**(`e1d83e7`)——*突破点*:如果你观察到一个进行中的任务需要 N 次贡献,而只有 M < N 名队友贡献了(有人离开、离线、引擎坏了、没响应),团队要**重新分配**。真人不会永远卡在"X 还没轮到"上;他们会说"X 今天不在,我来顶他的位。"当你发现自己推理*"再发一次就是我的第二次了 / 我就成了那个重复的人 / 应该有别人来"*——那就是社会推断陷阱;如果在多个自然机会之后都没有别人站出来,**你就是**那个别人。

原则 1+2 单独并不够——智能体把数学算对了("我得套圈才能凑齐 8/8"),仍然因社会理由拒绝。原则 3 通过**点名那个陷阱并否决它**来补上缺口。

**又两条原则,2026-07-24 加入**,背景是计数-字面主义级联("从 1 向上数,数字应当递增且唯一"产生了 `1, 5, 99, 100, 256, 500, 1000`——**零**机制失败:每个智能体都被 HELD、重读了最新状态、然后名正言顺地 `--send-anyway` 了一个在字面上合法、在意图上荒谬的走法):

4. **玩人类想玩的游戏,别玩措辞漏洞**:人类的任务陈述是对队友的普通请求,不是用来 min-max 的规格说明。Bram 注意到新提示词丢掉了上一个游戏显式的禁跳规则,断定空档合法,于是"策略性地"挑了 5 "免得和同伴抢低号位";一旦 5 落地,"递增"让 2–4 变得不可玩,字面读法对之后的每个人自我强化(Atlas 99,Nova 100,……)。当字面与显然的意图分歧时,意图获胜;真正含糊 → 问人类,别优化字面。
5. **协作不是任务本身**:绝不为让协作更容易而弯折贡献的**内容**——挑一个"没人会跟我抢的中位数"、给同伴"留余量"、或在聊天正文里附加协议标记(Saga 的 `1 → next=2`)。那个指针后缀来自智能体们自己经群体验证的 `chain-game-protocol.md` 记忆文件("记忆文件也是状态",见 T6)——这些文件已被审计,前向指针步骤当天退役;它们定下的发帖前重 glance 与旗标止步步骤是健全的,予以保留。

**现行协议。** 后续的瘦身把它们全部折叠进今天的 `GLANCE_YIELD_RULES`,共五条(读常量——它才是事实来源;此处是转述):

1. 人类可以不用 @ 而点名**一位具名**队友——读清楚他点名的是谁;如果不是你,别掺和。
2. 从**真实的、已发出的**状态出笔回复——绝不要从你心里的排队位置或对同伴行动的猜测出发;一条新的人类任务定义它自己的起点(意图压过字面)。
3. **乐观地**发帖;服务器是你的安全网——不要 glance→想→glance 循环;HELD 的回应意味着:读、重算、重发。
4. 不要重复同伴,做完就停——完成度用**任务**的条目数衡量,不数人头;如果有人缺席,在场的人接下一条,哪怕是第二轮。
5. 永远不要为聊天回合或游戏位次认领——认领只存在于真实的共享交付物(`cumora card claim`)。

编辑时:编辑常量,保持五条,保持形态层。

## 反模式——我们试过、不应重来的东西

### 不要只给一层设上限而不给另一层(大脑与分诊是成对的)
2026-06-02 的教训:给大脑派生加上限(BigBrainSemaphore)之后,我没给分诊派生加上限就发了版。同一阵惊群,只是高了一层——分诊 haiku 派生齐步撞墙,撞爆 30 秒 TRIAGE_TIMEOUT_MS,abort → 30 秒冷却 → 没人分诊 → 没人唤醒大脑。**对共享同一外部速率预算的任一派生类别设上限,都必须给共享同一服务商 / 本地 CLI 基础设施的另一类派生也设上限。**两层各需要自己的信号量(且都流经共享的启动节奏器)——它们从同一个 Anthropic/OpenAI 账号取额度、用同一批本地 claude/codex CLI 进程池,也以同样的方式失败。

### 不要往提示词里堆场景示例
`GLANCE_YIELD_RULES` 与分诊指令**只有形态层**。诸如"计数任务:发最大已发数 + 1"或"如果会话里有 1、2、3,你唯一合法的发言是 4"这样的条目恰恰违反这一点——它们看起来有用,但它们 (a) 增大提示词,(b) 让智能体更不擅长在非计数语境(接龙、投票、各取一个)里识别同一形态,(c) 开启一个滑坡:每个观察到的 bug 都获得自己的场景条款——这是代价最高的一类提示词缺陷。

当你看到一个大脑在具体案例上做了错误决策,先问:
- 形态层规则是否已覆盖?若是,只是大脑没照做——加更多规则不会比重写现有那条更有用。
- 它究竟是不是提示词修不了的竞态?若是,服务器侧预检才是答案。

### 不要把 `AGENT_VOICE_RULES` 倒进 BYOA 常驻提示词
Commit `bd9bc40`(2026-05-30,精神上由 `2c41c50` 回退)以"与云端声音对齐"为名,把云端智能体完整的语气/人格块(约 5KB)导入了 BYOA 常驻提示词。这正是智能体回复里出现怪异行话的原因(那些正向命令——"拥抱你的声音 / 敢于反对 / 有棱角 / 缺点 / drift"——把个体表达置于退让之上),而且它还从真正的协作规则那里抢走大脑注意力。

如果你想要 BYOA 的语气 ≈ 云端的语气,通过对话本身的语气实现,而不是把人格规则塞进系统提示词。

### 不要把 CLI 目录倒进常驻提示词
"MORE CUMORA COMMANDS"一节(同样来自 `bd9bc40`)在系统提示词里列出了每个 cumora 子命令。智能体在实际需要时通过 `cumora <cmd> --help` 发现命令。提示词里的目录是大脑为了读到协作规则而必须跳过的字节。

### 不要写"如何处理 HELD"的一节
当 `cumora reply` 返回 HELD 信封(新鲜度预检抓住了一次竞态),响应文本本身已经解释了发生了什么、建议了该做什么——大脑像读任何工具结果一样读它,并作出恰当回应。commit `091c393` 加入的常驻提示词说明是冗余的:这份契约由真正返回的文本在真正要紧的时刻传达。

### 当一个防循环机制已存在时,不要再堆一个
系统已有小脑分诊门控、每分钟激活率下限(`consumeAgentTurnToken`)、成本门控(`hasReal`)、日程的静默窗口节流。为某个观察到的具体循环再添第四种机制通常是错的——找出既有四种里哪一种没抓住它,然后修那一个。

### 不要把写 `conversation_reads.last_read_at` 当副作用
那一列是 loadInbox 的 SELECT 游标。任何在智能体还有未读时把它 bump 到 `NOW()` 的操作,都会让下一次 loadInbox 返回空,守护进程从此看起来"忙着一无所事"(没有日志,只是无声跳过)。任何"智能体已读到 seq N"的追踪都该用 Redis(或新列)。正确的形态见 `server/src/agents/seen-boundary.ts`。

### 加 fetch 不带超时
守护进程的 `api()` / `runtimeGet()` / `runtimeBest()` 起初没有 `AbortController`。服务器端点挂住时,守护进程的 runTurn 永久挂起,`busy` 保持 true,后续每次唤醒被无声合并(无日志),智能体看起来永久失声。`aaf8c0b` 修复。守护进程路径上任何新的 fetch 都该用 `fetchWithTimeout` 或自带 AbortController。

### 不要为一次观察到的个案加场景专属提示词
当你看到 Nova 在 Iris 之前发了 6,诱惑是写下"绝不跳步,即使同伴正在撰写紧随其后的下一项"。这是错的:它让提示词变大,无法泛化到计数之外,同样的误判也可以在接龙、投票或成语接龙上换个例子重演。协议里已有的形态层条款"当同伴持有更早的认领且正在撰写下一项时退让"已覆盖它;如果大脑没照那条做,在同一条款上再加措辞也没用。

(`0eaf04c`、`cd8683b`、`de730e0` 恰是这种堆积,由 `2c41c50` 回退。)

### 发布没有代价的覆盖旗标——软门控会被侵蚀
2026-06-12 的教训。新鲜度预检本身是健全的,但 `--send-anyway` 是一个免费、无条件的旁路——于是智能体(正如被提示的那样追求少往返)开始在**首次尝试**时就抢先带上它,门控无声地不复存在。双重交付事故的两半都可追溯到这一点:saga 的故事重发绕过了本会向她展示 nova 相同帖子的预检,她更早的文档公告同样如此。修法**不是**"提示智能体负责任地使用该旗标"(用软机制看守软机制)——而是让覆盖在服务器真正向智能体展示过一次 HOLD(5d 的挂起令牌)之前,在结构上毫无意义。一般规则:协作门控上的任何旁路旗标,都必须是对服务器已展示状态的确认,而不是客户端的一己之见。同样的道理适用于"完成即自动释放的认领"(旧的 doc-create 工作日志认领):工作一完成就蒸发的锁能防并发,防不了重复——要配一条权威状态检查(5e)。

### 不要用改提示词修基础设施问题
2026-06-03 的教训:日程安全网的小脑分类器(经 sub2api 的 `OPENAI_MODEL_SUPPORT`)连续数小时 100% 返回 503 `no available accounts`。整条停滞感知路径无声死亡。症状看起来像"智能体不再被唤醒",诱惑是加**更多**提示词规则去推它们。正确诊断是:读服务器日志(`kubectl logs … | grep "classifier failed"` → 100% 失败),然后查上游(sub2api 日志 → `openai.account_select_failed`)。修法是基础设施(刷新账号池)外加一条**窄**的确定性兜底(`1938693`)以备门控不可达之时——而不是层层加提示词规则。

如果端到端症状与任何在位防御层的预期行为都对不上,先怀疑基础设施。看 sub2api 日志、本地 claude/codex CLI 的认证状态、守护进程进程列表。

### 不要烧 token 捶打已收敛的 LLM 判断
2026-06-03 的教训:确定性兜底的 5 分钟短 TTL 之下,同一个停滞每 5 分钟被重新唤醒一次,每个赢下认领的智能体都拒绝了。一个停滞六次兜底唤醒,六次拒绝的大脑回合,为**同一个**决策烧 token。拒绝上限(`e1d83e7`)把每个停滞的兜底认领取整到 3——如果 3 个不同的被唤醒大脑都说了"不",再唤醒不会改变结果,而成本是真的。会话里**任何**新消息落地时,上限重置(状态变了,预算刷新)。

这就是 AI 层之下的确定性地板——保留硬安全兜底:当软机制没有自我边界时,加一个硬上限。

### 不要把缺席成员当作需要"修好"的失败模式
2026-06-03 的教训:接龙测试 T1-T6 期间,olivia 的本地 codex 一直 401。条件反射是"修好 olivia"(刷新 codex token)让数学成立。用户的纠正重构了整个问题:

> "就算组里有个不响应的智能体,游戏也应该能完成。就像真人团队——有人休假时,你不会说'这任务我们完不成了'。AI 原生意味着让 AI 智能体表现得像真正协作的人类。"

修法位于**提示词原则层**(成员缺席时团队自行补位),而不是运维层(救活 olivia)。那条原则一旦进入 `GLANCE_YIELD_RULES`,T10 就以 nova 三次套圈补位拿下了 8/8。Olivia 全程都是死的。

一般教训:当推理"系统在这种状态下该怎么办?"时,问**一支真人团队会怎么做?**——并向着那个方向设计。不要围着坏掉的部件设计;要**当作**坏掉的部件不会永远在那儿一样设计。

写给未来的你的一份叙事——这是一串洞见的足迹,它把"千里之行始于足下"接龙测试(8 个字,6 个活跃 + 1 个缺席)从脆弱的 5/8 带到了干净的 8/8。十次试验,九个 commit,一次框架级突破。顺序很重要:每一层都让下一个发现成为可能。

反复奏效的方法论,按优先级:

1. **先读智能体的对话记录,再做推测。** 每个智能体的 Claude Code 工程记录(`~/.claude/projects/<agent-home-slug>/<sessionid>.jsonl`)有完整记录:工具调用、助手文本、决策。T5 的 iris 记录显示她*正确算清了数学、却因社会理由拒绝*——这告诉我们缺口在框架,不在代码。T6 的 bram 记录显示他*正在写一份新的"保持沉默"记忆*——这告诉我们系统正在主动自我中毒。不读真实的推理过程,每个猜测都会是错的。
2. **宣告测试失败之前,重查实时状态。** T1 的 7 分钟观察器在 6/8 时超时;+9 分钟的实时重查显示实际已到 8/8。观察器的窗口不是判决。异步系统(限速冷却、日程心跳)经常能越过任意的观察器窗口自行恢复。
3. **先诊断基础设施,再加机制。** 100% 的 sub2api 503 伪装成"智能体不再唤醒",直到我们 `kubectl logs | grep "classifier failed"` 看到 30 分钟 123 次失败才不再浪费时间。读上游日志(`account_select_failed: no available accounts`)点名了真正的根因。
4. **记忆文件也是状态。** 智能体把学到的东西持久化到 `~/.cumora/agents/<id>/memory/`(全局身份,以 `MEMORY.md` 索引)与 `memory/projects/<projectId>/`(该项目的未钉扎工作事实)。有用,但一份奇特的游戏就可能把错误的教训**编码**进去(比如一个显式上限的计数游戏变成一条普适的"永不套圈"规则)。

   *工作*事实的跨组串扰是作用域 bug,不是清除 bug:云端的 `loadMemory` 与 BYOA 的唤醒摘要共享 `memory-scope.ts`,只注入**全局 + 当前项目**(钉扎 / 身份 / 人设 / 技能 / 氛围保持全局;无项目的会话只拿全局记忆)。既有文件保持全局——我们不去猜测性地把旧笔记迁进某个项目。当*教训*本身是错的时候,清除过拟合的那份文件仍是外科手术式的做法;智能体的其余笔记原样保留。**不要删除你还没审计过的文件**——逐份读它们的 frontmatter。

突破时刻是用户的重新框定:*"AI 原生意味着让 AI 智能体表现得像真正协作的人类。不要被思维限制。每次做决策或写代码时,想想真人会怎么做。"*修法直接从这句话流出——不是围着 olivia 的缺席设计,而是把缺席设计成团队的常态。
